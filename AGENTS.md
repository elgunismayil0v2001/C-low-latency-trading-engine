## 1. Goal and non-goals

tickbook is a C++20 tick-data replay engine and L2 order book for Binance spot data.

**The main purpose of this project is to demonstrate low-latency C++ code.** Every rule below serves that.
On top sits a small neural-network trading signal, built signal first, but it is secondary and must never
compromise the hot path.

Non-goals:
- Live trading or live-latency claims. All numbers are **replay processing latency on the stated hardware**
  (state the CPU and OS next to every number; the owner develops on an Apple M2, CI runs x86 Linux).
- Profitability claims. The free sample data is one day per month; at a few-second horizon, taker fees likely
  exceed any edge. Results are research evidence only, and a negative result is an acceptable, honestly reported outcome.
- ML frameworks inside the engine. Training is PyTorch, offline; inference is hand-written C++.
- Multi-symbol or multi-exchange support. One engine instance handles one symbol (default BTCUSDT).

### Starting point (what already exists)

Milestone 1 is in the repo, 23 tests passing:
- `types.hpp`: `Event` (48 bytes), `Side`, `EventType`, `Price`/`Qty` as `int64`.
- `fixed.hpp`: `parse_fixed` (decimal string to fixed-point, no floating point, rejects precision loss and overflow).
- `ring_buffer.hpp`: `SpscRing<T, Capacity>` lock-free SPSC queue with cached indices and cache-line-aligned counters.
- `book_map.hpp`: `BookMap`, `std::map` baseline L2 book (`apply`, `best_bid`, `best_ask`, level counts, `crossed`, `clear`).
- `sequencer.hpp`: `DiffSequencer`, Binance diff-depth synchronisation (`Drop` / `Apply` / `Resync`).
- GoogleTest tests, CMake with `TICKBOOK_SANITIZE`, CI matrix (g++ and clang++; plain, ASan+UBSan, TSan).

Build on this code; do not rewrite it. Known problems to fix first (milestone 2, items 2.1 to 2.4):
1. **Sequencer versus flattened events.** One Binance depth message becomes several `Event`s sharing
   `first_id`/`last_id`. Calling `DiffSequencer::on_message` once per `Event` falsely returns `Resync`
   (`first_id != prev_last_ + 1`), and a message with no levels produces no `Event`, so gaps go unseen.
2. **`Event` padding.** `sizeof(Event) == 48` includes 6 bytes of trailing padding; written to a file it is
   uninitialised, making files nondeterministic.
3. **`DiffSequencer` has no reinit** after a `Resync`.
4. **CI.** GoogleTest `FetchContent` has no `URL_HASH`. If clang + TSan fails on `ubuntu-24.04` with
   "unexpected memory mapping", add `sudo sysctl vm.mmap_rnd_bits=28` before the tests (verify it is needed first).
5. **Missing tests:** `parse_fixed` with `"1."`, `".5"`, `"+1"` and scale 0; sequencer behaviour after `Resync`;
   negative `qty` in `BookMap`.

## 2. Hot-path rules (highest priority)

The hot path is: ring pop -> book update -> feature update -> signal (and the sequencer on the live path).

1. **No heap allocation after startup.** `BookMap` is the deliberate baseline that breaks this; every other
   hot-path component must not allocate. Preallocate everything, including rings, book storage and feature windows.
2. **Fixed-point only.** `Price` and `Qty` are `int64`. Use `2*mid` as an exact integer rather than a half-tick mid.
   `float` is allowed only at the feature-to-NN boundary and inside `nn/`, converted in exactly one function.
3. **No `virtual` calls, locks, exceptions, I/O or `std::function` per event.** Runtime polymorphism only at
   `EventSource` and `IStrategy` boundaries and in offline tools.
4. **Memory layout is a design decision.** Keep hot data contiguous, align shared counters to cache lines
   (`kCacheLine = 128`), avoid false sharing, prefer flat arrays to pointer-chasing, avoid branches on unpredictable data.
5. **SPSC discipline.** Exactly one producer and one consumer per `SpscRing`. Every memory order must carry a
   comment saying why it is sufficient.
6. **Measure first, then optimise.** No performance change without a before and after benchmark.
7. **No look-ahead.** A feature at time `t` uses only events with `ts <= t`. Labels exist only in offline tools.
8. **Determinism.** Same input file and same config must produce bit-identical output (book states, features, signals).
9. Re-check the Binance diff-depth sync rules against the current official docs whenever the sequencer is touched.
10. **No page faults on the hot path.** Touch all preallocated memory before the measured loop; on Linux use `mlock`,
    and `MAP_POPULATE` or `madvise(WILLNEED)` for the `mmap` replay. Count minor faults (`getrusage`) around the
    measured loop and assert 0.
11. **Threads.** On Linux pin producer and consumer to separate physical cores (`sched_setaffinity`). macOS cannot pin;
    document that as a limitation. The consumer busy-spins with a CPU pause hint (no blocking, no syscalls) in latency
    runs; a yield fallback is allowed elsewhere.
12. **Errors and logging.** No exceptions, `printf` or logging on the hot path. Errors are status codes and counters
    (dropped, resync, parse-reject) read after the run.
13. **Build flags for hot-path targets** (`replay`, benchmarks): `-O2` or `-O3`, evaluate LTO and `-fno-exceptions
    -fno-rtti`, and keep a flag only if the benchmark shows a gain. Prefetch hints, `[[likely]]`/`[[unlikely]]` and
    huge pages only with benchmark evidence.

## 3. Architecture

```
EventSource (CsvSource | BinaryReplay | LiveFeed)     runtime interface, off hot path
  -> SpscRing<Event>                                  hot path, compile-time
  -> [DiffSequencer <- SnapshotLoader]                live path only (see section 4, data)
  -> OrderBook (BookMap | flat vector | offset array) policy templates, same interface
  -> FeatureEngine                                    hot path, incremental O(1)
  -> Signal (rule | MLP)                              hot path
  -> IStrategy -> SimExchange -> Metrics              runtime Strategy pattern
FeatureEngine -> dump (ts, features, labels) -> python/ PyTorch -> weights.bin -> C++ MLP
```

Threads: one producer thread (EventSource -> ring) and one consumer thread (everything after the ring).
Replay mode is lossless: if the ring is full the producer waits. Live mode counts overflows and treats one as a resync.

Interfaces (describe in code with concepts or small abstract classes; keep signatures minimal):
- `EventSource`: pull-based, returns the next `Event` or end-of-stream. Runtime interface (adapter pattern).
- `OrderBook` concept, satisfied by `BookMap` and the flat/offset books: `clear`, `apply(Event)`, `best_bid`,
  `best_ask`, `bid_levels`, `ask_levels`, `crossed`, and a way to visit the top K levels per side without allocating.
- `ILabeler`: offline only. `IStrategy`: runtime interface taking a signal and the book view, returning order intents.

**One feature code path.** Training features come from the same C++ `FeatureEngine` used in replay and live.
Never reimplement features in Python.

## 4. Data and formats

### Source data (Tardis free CSV)
Free files cover the first day of each month, gzipped CSV, URL pattern
`https://datasets.tardis.dev/v1/binance/{incremental_book_L2|trades}/YYYY/MM/DD/BTCUSDT.csv.gz`
(verify the exchange id and pattern against the docs before scripting any download).

- `incremental_book_L2` columns: `exchange, symbol, timestamp, local_timestamp, is_snapshot, side, price, amount`.
- `trades` columns: `exchange, symbol, timestamp, local_timestamp, id, side, price, amount`.
- `timestamp` and `local_timestamp` are **microseconds** since epoch, UTC. Event `ts_ns` = `timestamp * 1000`.
  `local_timestamp` is arrival time; use `timestamp`, and `local_timestamp` only for tie-breaking checks.
- `amount` is absolute, not a delta; `amount == 0` removes the level. `side` for trades is the aggressor side.
- A file may begin with non-snapshot rows: skip rows until the first `is_snapshot=true`. If a snapshot row follows a
  non-snapshot row, clear the book first.
- Row order is capture order. For equal timestamps use row position as the tie-breaker. Merging the book and trades
  files: stable merge by `timestamp`, book rows before trade rows on ties; document this and test determinism.
- **These files contain no Binance `U`/`u` update ids.** Replay from CSV therefore does not use `DiffSequencer`;
  the vendor's sequencing is trusted, and `first_id`/`last_id` are 0. `DiffSequencer` and `SnapshotLoader` are used
  only by the live recorder (milestone 8), where `Event` carries real ids.
- Message boundaries: group consecutive rows with identical `local_timestamp` into one message and set the
  end-of-message flag on the last row. Features and signals are evaluated at message boundaries, never mid-message
  (a book can be transiently crossed inside a message).
- Scales: BTCUSDT default `price_scale = 2`, `qty_scale = 8`, configurable per symbol; the converter must fail loudly
  (using `parse_fixed`'s rejection) on any precision loss. Verify the symbol's tick and step size.
- **Licensing:** Tardis data is licensed; never commit or redistribute it, and do not commit excerpts unless the owner
  has confirmed the terms allow it. Test and benchmark fixtures are produced by a deterministic synthetic generator
  (`tools/gen_synthetic`: seeded random-walk book with snapshot, updates, removals and trades, in the same CSV format).
- Day files are large (compressed, then hundreds of MB to GBs expanded): stream them, never load a whole file.

### Binary event file (written by `csv_to_bin`, read by `BinaryReplay` via `mmap`)
- 64-byte header: 8-byte magic, `u32` format version, `u32` endianness marker (`0x01020304`), `u32` event size (48),
  `i32` price scale, `i32` qty scale, 16-byte symbol, `u64` event count, remaining bytes zero.
- Then a packed array of 48-byte `Event`s, 8-byte aligned.
- `Event` layout stays 48 bytes: `ts_ns, first_id, last_id, price, qty` (5 x 8 bytes), `type, side, flags` (3 x 1 byte),
  5 explicit zeroed pad bytes. `flags` bit 0 = end-of-message. Keep the `static_assert`s on size and trivial copyability.
- The reader rejects a wrong magic, an unknown version, a wrong endianness marker or a wrong event size, and a count
  that does not match the file size.
- Converter output must be byte-identical across runs (determinism test via checksum).

### Weights file (`weights.bin`, written by `python/export_weights.py`)
8-byte magic, `u32` version, `u32` endianness marker, `u32` layer count and each layer's dimensions and activation id,
`float32` input mean and std arrays, then per layer row-major `float32` weights and biases, then a CRC32 of the payload.
The C++ loader validates all of it and fails with a clear error; it never reads out of bounds.

## 5. Correctness gates

- Builds with no warnings under `-Wall -Wextra -Wpedantic -Wshadow` on g++ and clang++.
- All tests pass plain, with ASan+UBSan, and with TSan.
- **Golden-file replay test:** a small fixed input must reproduce a fixed final book, event count and checksum.
- **Differential test:** random event streams applied to `BookMap`, the flat-vector book and the offset-array book
  must give identical best bid/ask, level counts and top-K contents after every event.
- **Determinism test:** two runs on the same file give identical output.
- Binary formats are versioned and validated on read.
- Walk-forward splits only for any model work; never shuffle. Purge samples whose label window crosses a split.
- New behaviour has a test. A bug fix has a regression test that failed before the fix.

### 5.1 Testing strategy

- **Unit tests:** one test file per header or tool, GoogleTest. Cover edge cases, not only the happy path.
- **Fixtures:** tiny committed files under `tests/data/` (a few KB: a short Tardis CSV excerpt, its expected binary file
  checksum, a tiny `weights.bin`). Tests never touch the network and never need real market data.
- **Concurrency tests:** ring buffer and the producer/consumer replay under TSan, with a stress test (millions of
  items, tiny capacity) that checks order and loss.
- **Fuzz targets** (libFuzzer, clang, with ASan+UBSan) in `fuzz/`: `parse_fixed`, the CSV line parser, the binary
  header and event reader, the weights loader, and `DiffSequencer` message sequences. Commit a small seed corpus.
  Any crash found becomes a regression test.
- **Property/differential tests:** books against each other (section 5); features against a slow, obviously correct
  reference implementation in the test file.
- **Python tests** (`pytest` under `python/tests/`): export determinism with fixed seeds, the C++/PyTorch parity
  vectors, split purging (no label window crosses a split), no shuffling.
- **Coverage:** report line coverage of `include/` with gcov or lcov as an informative CI artifact; do not chase a
  number, but every new branch in hot-path code should be exercised by a test.

### 5. Signal first: features and evaluation
- 5.1 `FeatureEngine`: incremental O(1) per message, fixed-size output struct, no allocation. Features (K = 5 levels default):
  - `spread_ticks`.
  - `imbalance_l1` = (bid qty - ask qty) / (bid qty + ask qty) at the best level, and `imbalance_k` over the top K levels.
  - `microprice_offset` = microprice minus mid in ticks, with integer-exact arithmetic and documented rounding.
  - `ofi_w` = order flow imbalance at the best level (Cont, Kukanov and Stoikov): per message
    e = [bid_price >= prev_bid_price] * bid_qty - [bid_price <= prev_bid_price] * prev_bid_qty
        - [ask_price <= prev_ask_price] * ask_qty + [ask_price >= prev_ask_price] * prev_ask_qty,
    summed over a rolling window of W messages (defaults 10, 50, 200) using a preallocated ring.
  - `trade_flow_t` = signed traded quantity (aggressor buys minus sells) over rolling time windows (defaults 100 ms, 1 s).
  - `mid_return_t` = mid change in ticks over rolling time windows (defaults 100 ms, 1 s).
  Unit-test each feature against a hand-computed example.
- 5.2 `dump_features`: sample the feature vector on a fixed time grid (default every 100 ms of event time), write
  `(ts, features, forward mid returns for each horizon)` to a binary or Parquet file with a versioned header.
  Forward mid at horizon H = mid at the first sample with `ts >= t + H`; discard samples without one.
- 5.3 `eval_signals`: for each feature and horizon in {1 s, 3 s, 10 s}, report information coefficient (Spearman),
  hit rate on non-flat moves, and the decay curve; also report per-hour or per-day blocks so stability is visible.
  Always include two baselines: the sign of `imbalance_l1`, and logistic regression on all features.
  If nothing shows out-of-sample edge, stop and report the result; do not build more on top of it.

### 6. Labelers, training, C++ inference
- 6.1 `ILabeler` (offline, Strategy pattern):
  - `DirectionLabeler`: 3 classes (down, flat, up); flat means |forward mid return| < `k` ticks (start `k = 1`, tune on training data only).
  - `ReturnLabeler`: regression on forward mid return in ticks.
  Both write the same dump format with a label-kind field. Labelers never appear in hot-path headers.
- 6.2 `python/train.py`: PyTorch MLP (two hidden layers, about 32 units, ReLU). Cross-entropy with class weights for
  direction, Huber loss for return. Walk-forward split by whole days in time order with purging of H at boundaries.
  Fixed seeds, config in a file, metrics written next to the weights. Must be compared against the section 5.3 baselines.
- 6.3 `export_weights.py` -> `weights.bin` (section 4) with normalisation statistics from the training split only.
- 6.4 C++ MLP inference: hand-written, float32, no allocation after load, scalar baseline first; an optional SIMD
  or int8 variant only if benchmarked against the scalar one. Convert features to float in exactly one function.
- 6.5 **Parity test:** C++ output matches PyTorch within 1e-5 on 1000 fixed vectors, run in CI from a committed tiny weights file.
- 6.6 Benchmark inference per call; it must fit the section 4.4 budget or the design is not accepted.

### 7. Strategy and simulated exchange
- 7.1 `IStrategy` implementations: threshold rule on the signal, then the NN signal (runtime Strategy pattern).
- 7.2 `SimExchange`: orders are submitted at time `t` and become active at `t + latency` (configurable); market orders
  fill by walking the replay book at the active time (no market impact on the recorded data, stated in the report);
  fees configurable (set to the current Binance fee tier, verify before use); position and size limits; mark to mid.
  Optional later: passive orders with a documented queue-position model.
- 7.3 `Metrics`: gross and net P&L, trade count, turnover, average P&L per trade in basis points against fees,
  max drawdown, hit rate, **break-even fee**, and the engine latency histogram. The report states plainly if the
  result is not distinguishable from zero given the sample size.

### 8. Live recorder
- 8.1 WebSocket `<symbol>@depth@100ms` plus REST depth snapshot; apply the `DiffSequencer` rules from the current

- 8.2 Replay of a recorded file must reproduce the live book (golden test against logged top-of-book samples).

## 8. Writing about results

README tables and reports must state hardware, compiler, flags, dataset (symbol, date) and run count. Report medians
and tail percentiles, not best runs. Do not describe replay latency as trading latency, and do not describe a
backtest on one day as evidence of profitability.
